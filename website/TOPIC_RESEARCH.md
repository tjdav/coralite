# Coralite topic research

A repeatable, data-driven backlog for Coralite blog posts and docs pages. The pipeline is adapted from Euroloom's `docs/blog-research.md`, with the directory-specific signals replaced by Coralite's docs, benchmarks, diagnostics and transcripts.

The working document is [`BLOG_BACKLOG.md`](./BLOG_BACKLOG.md). The machine-readable versions live in `data/topics/`.

## Why

A topic is only worth writing when it has:

1. real demand,
2. intent that fits a post or a docs page,
3. a realistic SERP,
4. enough coverage and evidence in Coralite to answer authoritatively,
5. enough editorial signal to be worth your time.

The scorer makes those constraints explicit instead of relying on intuition.

## Signals

| Source | What it provides | Where it comes from |
|---|---|---|
| Keyword Planner CSV | Avg. monthly searches | Manual Google Ads export (see below) |
| Search Console CSV | Impressions, clicks, position | Manual export; optional while the site is new |
| Community counts | Hacker News stories, Stack Exchange questions, GitHub issues | Free APIs, no key required. GitHub counts are capped at a 0-3 contribution so broad issue searches cannot dominate. |
| SERP results | Weakness (1-5) and ecosystem density | SerpApi, or a manual browser export |
| Docs inventory | Whether a canonical page exists | `src/pages/docs/**/*.html` |
| Benchmarks | Answerability evidence | `../benchmarks/` |
| Transcripts | Editorial priority and candidate phrases | `data/topics/transcripts/` |

Demand combines volume, impressions, community mentions and SERP density. Missing signals are dropped and the remaining weights renormalised. A topic is only `ready` when at least one demand signal exists.

## Keyword Planner (manual)

Google Keyword Planner has no turnkey free API, so this step is a manual export.

1. Open **Google Ads** → **Tools & settings** → **Planning** → **Keyword Planner**.
2. Choose **Discover new keywords** → **Start with keywords**.
3. Paste a batch from `data/topics/keyword-planner/seeds-by-cluster.md` (generated by `seed`).
4. Set targeting deliberately and record it: Worldwide, English, Google Search only.
5. Ensure **Avg. monthly searches** is visible. **Competition** is optional.
6. Download → **Keyword stats** (not Campaign forecast, not Forecast).
7. Drop the raw file into `data/topics/keyword-planner/`.
8. Run `pnpm --filter website topic-research merge:keywords`.

The importer handles Google's UTF-16 tab-separated exports, ranges such as `1K – 10K` (lower bound is used), and comma-separated CSVs. A `manual*.csv` file in the same directory overrides exports and is never overwritten by a re-merge.

Write `data/topics/keyword-planner/settings.json` with `location`, `language`, `network` and `exportedAt` so the volumes remain interpretable later.

## Search Console (optional)

While the site is new, this export is unlikely to be useful. When it is:

1. Search Console → Performance → Queries.
2. Export the CSV.
3. Save it as `data/topics/search-console.csv`.

The scorer picks it up automatically and reweights demand.

## SERP collection

SerpApi is the canonical provider. The key can come from the environment or from any dotenvx-encrypted file, so the key from Euroloom can be reused without copying it:

```bash
# From the website workspace, using the Euroloom encrypted env file
pnpm --filter website exec dotenvx run -f ../../euroloom/.env -- \
  node scripts/topic-research.js collect:serp --provider serpapi --limit 25
```

Or pass the file explicitly to the script:

```bash
pnpm --filter website topic-research collect:serp --provider serpapi \
  --env-file ../../euroloom/.env --limit 25
```

The key is never logged. The free plan allows roughly 250 searches per month, so:

- `--limit 25` is the default for `collect:serp`.
- `--dry-run` lists the keywords before any request is made.
- Results are cached in `data/topics/serp-results.json`; `reclassify` recomputes weakness and density offline.
- `--only "reason fragment,another fragment"` restricts a run to a shortlist.

Without SerpApi, export the top 10 results per keyword into `data/topics/serp-export.csv`:

```csv
keyword,position,title,url
web components without shadow dom,1,Example title,https://example.com/post
```

Then run `collect:serp --provider file`.

### Weakness rubric

| Class | Examples | Weight |
|---|---|---|
| `giant` | React, Astro, MDN, Google, Microsoft | 0.00 |
| `authority` | web.dev, W3C, Wikipedia, Chrome docs | 0.15 |
| `peer` | Lit, Stencil, Eleventy, WebC, Hugo | 0.50 |
| `vendor` | product docs | 0.45 |
| `competitor` | staticgen, Jamstack directories | 0.70 |
| `directory` | GitHub, npm, dev.to, Hacker News | 0.80 |
| `forum` | Reddit, Stack Overflow, forums | 0.95 |
| `other` | unknown blogs | 0.55 |

The weighted mean maps to a 1-5 weakness score. Six or more directory/competitor/peer results lift the score to at least 4; three or more giants, four or more authority sites, or eight or more vendor pages cap it at 2.

Density is the number of distinct non-giant, non-authority domains in the top 10. It acts as a demand proxy: if nobody targets the query, the ecosystem does not care about it yet.

## Transcripts

Place `.md` or `.txt` files in `data/topics/transcripts/`.

```bash
pnpm --filter website topic-research extract:transcripts
pnpm --filter website topic-research collect:transcripts
pnpm --filter website topic-research seed
```

`extract:transcripts` proposes repeated phrases; review the list and promote the useful ones manually. `collect:transcripts` feeds the editorial multiplier (up to +20% for frequently mentioned topics).

Transcripts are deliberately **not** treated as demand. They tell the scorer what you already care about, not what the market is searching for.

## Coverage and answerability

- `docs` in the seed catalog points at a canonical page. If it exists, coverage is `canonical`.
- Without an explicit page, the auditor matches keyword tokens against docs titles, descriptions, headings and existing editorial blog posts. A 50% token match is `partial`; otherwise `none`.
- Only a docs-level match satisfies the docs requirement. Editorial coverage can raise the score of a `blog-only` topic but does not count as documentation.
- Evidence is a list of repo references (tests, benchmarks, shipped code). Zero evidence produces `needs-evidence`.

Topics with an action of `docs+post` or `docs-first` and no docs coverage are marked `needs-docs`. Write the docs page first, then the post links to it. `blog-only` topics are not blocked by missing docs.

Curated topics, transcript candidates and the strategic clusters (`light-dom`, `validation`, `performance`, `migrations`, `ai-workflow`) are never marked `skip` for a competitive SERP. They carry a `competitive-serp` blocker instead and appear in the report's strategic section.

## Commands

```bash
pnpm --filter website topic-research seed
pnpm --filter website topic-research merge:keywords
pnpm --filter website topic-research collect:community --limit 40
pnpm --filter website topic-research collect:serp --limit 25 --dry-run
pnpm --filter website topic-research collect:serp --limit 25
pnpm --filter website topic-research reclassify
pnpm --filter website topic-research audit:coverage
pnpm --filter website topic-research score
pnpm --filter website topic-research report
```

`score` writes `data/topics/backlog.json`, `backlog.csv`, `backlog.md` and a copy at `BLOG_BACKLOG.md`.

`data/topics/seed.json` is generated. Add or edit curated topics in `MANUAL_TOPICS` in `scripts/lib/topic-research/seed.js`, then re-run `seed`.

## Statuses

| Status | Meaning |
|---|---|
| `ready` | Demand, coverage and evidence are all present |
| `needs-docs` | The docs page must exist before the post |
| `needs-evidence` | No test, benchmark or shipped code backs the claim |
| `needs-data` | No demand signal yet |
| `skip` | Navigational intent or a SERP dominated by giants |

Release posts are still generated by the release tooling from `changelog.json`. This pipeline only covers evergreen posts and docs pages.
