The Expensive Way to Find Out You Were Wrong

Runtime feedback costs a browser, a test harness and an interpretation step. Compile-time feedback costs a save. The difference is not speed — it is the difference between a puzzle and a task.

Thomas David November 19, 2026 · 9 min read

I've started taking the feedback loop for granted. Not in the abstract way people mean when they say “developer experience.” In a specific way: I've been writing Coralite components for long enough that when something breaks, I expect a line number and a suggested fix. I expect to find out I was wrong in about the time it takes to save a file.

And because I expect it, I've stopped noticing that it's unusual. Which means I've also stopped being able to describe what it was like without it.

So this post is an attempt to describe it, and to point at the thing that makes it possible.

The triple cost

The standard front-end lifecycle places detection late. You write the thing, you run the thing, and if it's wrong you find out from a browser.

That's the first cost, and it's the obvious one. A runtime error in a React component needs a browser or a headless browser. It needs the app in a state where the component renders. It needs you to look at the error, work out what it means, and trace it back to a line.

The second cost is setup. Getting a browser into a state where it can test the thing you care about is not free, and it's not a one-time cost — it's a cost you pay again every time the surface area changes.

The third cost is the one nobody budgets for, and it's the biggest: time to figure out what you want to test. The first two costs are infrastructure. This one is design. You have to hold the intended behavior in your head, translate it into an assertion, and hope the assertion is about the thing that's actually broken rather than the thing that's easy to assert.

Playwright is the honest version of this. It's a good tool, and the reason it's good is that it's solving a hard problem — end-to-end tests verify the assembled system, which is the only place certain classes of bug exist. But the loop is: write it, run it, wait for the browser, read the failure, work out whether the failure is the bug or the test.

If you're doing that with an AI in the loop, the cost compounds. The model proposes a change, the browser runs, the test fails, the model reads the failure, the model proposes another change. Every iteration costs a browser launch and a few thousand tokens. It works. It's just slow enough that you start avoiding it.

What e2e actually catches

Before I say anything about compile-time detection, I want to be precise about what it doesn't replace.

End-to-end tests catch integration failures, real browser behavior, timing, third-party scripts, network conditions, and the entire class of bugs that only exist when the system is assembled. Static analysis will never catch a race condition between two components. It will never catch a layout that breaks at a specific viewport. It will never catch the bug that only appears when a real user with a real password manager autofills a form.

A large class of errors was being pushed into an expensive medium when a cheap one was available.

The claim isn't that compile-time replaces end-to-end testing. The claim is narrower and more interesting. An undeclared ref is not a race condition. A template token that doesn't resolve is not a layout bug. These are facts about the source that are true or false before anything runs — and if you don't catch them at that point, you catch them later, in the medium that costs a browser.

Detection and remediation are different products

Here's the distinction that took me a while to articulate, and it's the one that matters.

Detection tells you something is wrong. Remediation tells you what to do about it.

Most tools do the first. Some do it very well — a good type checker will tell you exactly which line and exactly which type. But the second is what changes the loop, because remediation is what turns a failure into a step.

A failure without a next step is a puzzle. A failure with a next step is a task.

A catalogue, not a list

Coralite's diagnostics are documented as a single catalogue at /reference/diagnostics/. Every code the framework can emit, grouped by domain, with its severity, whether coralite fix can repair it, and how to resolve it. Today that catalogue holds 52 codes — 41 errors, 11 warnings, and 12 that coralite fix can repair without a human decision.

Three examples show the shape better than the whole list would.

E201 — an expression in a template. A token like {{ count + 1 }} is rejected because templates hold flat identifiers and nothing else. The remediation is to lift the expression into a getter, and coralite fix performs that transformation: it names the getter, adds it to export const getters, and rewrites the token. There is no decision to make, only a shape to apply.

E202 — a ref that no element declares. refs('increment') in client() is checked against the template. When exactly one candidate element exists, the fixer injects ref="increment". When the target is ambiguous, it refuses and says so — a deterministic tool that knows when it cannot be deterministic.

E301 — a module-scope import used in client(). The client block is serialized to the browser, so a static import cannot be referenced by name there. The fix rewrites it to await import() inside the block, which keeps the module out of the serialized function.

The rest of the catalogue works the same way: PAGE-201 catches a page script reaching into a component's internals, A101 catches an <img> without alt, E302 warns when observe() mutates state, and the three CFG codes stop the build on CSP configuration mistakes. Component diagnostics can be silenced with a pragma when a finding is intentional; configuration and route errors abort the build and cannot be ignored.

The catalogue is also queryable from the CLI, so you never need the browser to see the list:

coralite diagnostics coralite diagnostics --family plugin --fixable coralite diagnostics --search template --format json

Why the validator can be complete

The thing I want to be honest about is that the validator isn't clever. It's possible.

Every code in the catalogue is catchable because the constraints are strict. Templates hold tokens and nothing else, so every hole in a template is a declared symbol — which means E205 can check that every token resolves, and E201 can reject anything that isn't a flat identifier, without parsing an expression grammar. Named exports mean client and server are known top-level statements, so E301 can check what client() references without doing dataflow analysis. Attributes are declared objects, so E101 can reject an Array type at the point of declaration rather than at the point of use.

A framework where logic lives in templates and imports live at module scope can't enumerate its own errors. It would have to run the thing and see what breaks. That's not a criticism of those frameworks — it's a consequence of a different set of constraints, and those constraints buy things that matter too.

If the syntax is open, the space of errors is unbounded. Coralite's constraint set is small and closed, so the error space is enumerable.

That doesn't mean it catches everything today. It means the list is finite, the gaps are known, and coverage can grow toward a boundary rather than chase one.

Suggested fixes and deterministic fixes

The catalogue distinguishes two kinds of remediation, and the distinction matters more than it looks.

Every code has a suggested fix — the Fix. line that tells you what to do. E102 says to keep required and drop default, or keep default and drop required. That's a decision the tool can't make for you, because it depends on what the attribute is for.

Twelve codes are auto-fixable, and those are deterministic rather than suggestive. The catalogue names the AST transformation coralite fix applies, and those fixes are structural transformations on the same file. A deterministic repair means the same input produces the same output, and the output is a shape rather than a guess about what you meant.

Here is a real run against a component with an inline handler and a module-scope import used inside client(), abridged to one finding:

$ coralite check src/components/ui-counter.html ┌─ [CORALITE-E301] Top-level import 'log' referenced inside client() block. │ File: src/components/ui-counter.html:15:5 ├─ Code Context ──────────────────────────────────────────────────────────────── 14 | export async function client ({ state, refs, signal }) { > 15 | log('mounted') | ^ 16 | refs('button').addEventListener('click', () => { ├─ Why this failed ───────────────────────────────────────────────────────────── │ Top-level imports cannot be referenced inside client() block as client code │ is executed in browser context. ├─ Suggested 1-Shot Fix ──────────────────────────────────────────────────────── │ Convert top-level import 'log' to dynamic import inside client() │ const { log } = await import('../utils/log.js') └───────────────────────────────────────────────────────────────────────────────

And the transformation the fixer applies:

<template id="ui-counter"> - <button ref="button" type="button" onclick="increment()"> + <button ref="button" type="button"> Count is {{ count }} </button> </template> <script type="module"> - import { log } from '../utils/log.js' export function server () { return { count: 0 } } export async function client ({ state, refs, signal }) { + const { log } = await import('../utils/log.js') log('mounted') refs('button').addEventListener('click', () => { state.count++ }, { signal }) } </script>

And that's why --dry-run exists. Auto-fix on code you don't understand is dangerous, and a tool that rewrites your source without showing you the diff first is asking for a kind of trust it hasn't earned. So you preview, you read, you apply.

The AI loop, briefly

I said at the top that the AI loop is expensive, and the remediation side is where that changes. You don't have to feed a model heaps of instructions about how Coralite works. You run coralite check, you read the code and the suggested fix, and you fix the thing. --format json gives you the same information in a shape an agent can parse, and the pragma comments let a single finding be silenced without silencing the rest.

That's a separate post, because the workflow it enables is different enough to deserve its own. But it's worth saying here that the reason it works is the same reason the validator works: the codes are contracts. They're stable across releases, safe to match in CI, and the same strings appear in coralite check, the JSON report, and the reference page.

All just regular HTML and CSS

The thing I keep coming back to is that none of this required a new syntax.

The component is an HTML file. The template is HTML. The styles are CSS with :host and ::slotted. The logic is JavaScript in a <script type="module"> block, using named exports. The validator checks all of that without a browser, and the auto-fixes are AST transformations on the same file.

So the loop is fast, and the thing that makes it fast is the thing that makes it legible: there's nothing in the source that isn't HTML, CSS, or JavaScript. Which means when the tool tells you what's wrong, it's telling you about code you can read, in vocabulary the platform already owns.

The full catalogue is at /reference/diagnostics/ — 52 codes, grouped by domain, with every fix and every auto-fixable transformation named. If you're evaluating Coralite and want to know what it catches before you commit, that page is the honest answer.
