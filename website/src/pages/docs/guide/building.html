Building Applications

Guide

One build, several delivery targets. The same output serves the web, installed web apps, desktop shells and mobile shells; the adapter decides the edges.

Coralite compiles a component tree into portable HTML, CSS and ES modules. How that output is delivered is a separate decision. The default build is static, and the same artifact can be hosted on a CDN, installed as a web app, or packaged inside a desktop or mobile shell.

This page covers the build artifact first, then the web delivery modes, then the shell targets. The platform model is described in One Runtime, Every Platform.

1. The build artifact

coralite build writes one HTML file per route, the component and page CSS, the JavaScript needed by components that declare client behavior, and copied public assets. There is no Node.js runtime requirement in that output.

  • No client JavaScript by default: a component with no client(), no reactive state and no slots ships markup and CSS.
  • Server code is removed: server() runs at build time and is stripped from the browser bundle.
  • Assets are content-addressed: stylesheets and scripts are hashed so a target can cache them aggressively.
  • Incremental builds are route-aware: each dynamic output records a cache key derived from its route params and resolved server() state, so changing one data record rebuilds only the affected output.

Everything after this point is about how the artifact is served and which platform APIs the app can reach.

Development server

coralite dev does not pre-render dynamic outputs. Static, virtual, and plugin-generated pages build at startup; each dynamic route renders on request and enters a bounded LRU cache. Production builds remain uncapped and render every enumerated path.

Large data-driven sites can reduce the development route set explicitly:

import { defineConfig } from 'coralite' export default defineConfig({ // ... dev: { maxPages: 1000, maxCacheEntries: 256, routeFilter: ({ params }) => params.id.startsWith('public-') } })

routeFilter runs before maxPages and receives { params, page, index, app }. Routes excluded by the filter or beyond the cap return 404 in development only. paths({ app }) can also branch on app.options.mode to return a smaller set in development.

2. Web target

Static output

The default delivery is static HTML on a CDN, object store or any static host. Navigation uses standard links. View Transition crossfades can be enabled in coralite.config.js for app-like transitions without a client router.

<template id="nav-header"> <header class="site-header"> <nav> <a href="/">Home</a> <a href="/docs/guide/">Documentation</a> <a href="/blog/">Blog</a> </nav> </header> </template>

Best for: documentation, marketing sites, publications, catalogs and any interface where first paint and indexability matter most.

Hybrid data

The page shell is static and user-specific data is fetched after hydration. This is the right default for authenticated web apps: the framework does not expose request or response objects to server(), so the static build has no session to read.

<template id="user-profile"> <div class="profile-card"> <span ref="status" class="status-badge">Loading session...</span> <h3>{{ userName }}</h3> <p>{{ userEmail }}</p> </div> </template> <script type="module"> export const getters = { userName: ({ state }) => state.user ? state.user.name : 'Guest', userEmail: ({ state }) => state.user ? state.user.email : 'Not signed in' } export async function client ({ state, refs, signal }) { const status = refs('status') try { const response = await fetch('/api/user', { signal }) if (response.ok) { state.user = await response.json() status.textContent = 'Authenticated' status.classList.add('active') } else { status.textContent = 'Unauthenticated' } } catch (error) { if (error.name !== 'AbortError') { status.textContent = 'Failed to load user' } } } </script>

Best for: dashboards, account settings, live widgets and portals. The authentication mechanism belongs to the target: cookies, bearer tokens or a platform adapter that injects the signed-in user through plugin context.

SPA router

The opt-in router plugin swaps only an outlet region, so elements outside it survive navigation. Persistent audio, connected sockets and a shared shell all become possible without a separate application framework.

import { defineConfig } from 'coralite' import router from 'coralite/plugins/router' export default defineConfig({ plugins: [ router({ outlet: 'data-router-outlet' }) ] })

Every route is still a real pre-built HTML file. The router fetches that HTML and replaces the outlet in the browser. Pages without an outlet are wrapped automatically unless autoWrap: false is set.

<!DOCTYPE html> <html lang="en"> <head> <title>App Dashboard</title> </head> <body> <app-navbar></app-navbar> <audio-player></audio-player> <div data-router-outlet> <h1>Dashboard</h1> <p>Welcome to your workspace.</p> </div> </body> </html>

Guards are registered with beforeEach. Register app-wide guards in a persistent shell outside the outlet, and unregister route-scoped guards on the component's signal.

export function client ({ router, signal }) { const dispose = router.beforeEach(({ to }) => { if (to.path.startsWith('/app') && !localStorage.getItem('auth_token')) { return '/login/' } return true }) signal.addEventListener('abort', dispose, { once: true }) }

See the SPA Router Guide for outlets, persistent elements, guards, navigation events and state across route swaps.

3. Installed web

The same static output can be installed with a manifest, icons and, when offline start is required, a service worker. Installation changes how the app is launched, not how it renders. Manifest generation and service worker caching are project or plugin concerns; core does not assume either.

4. Desktop shell

Package the output in an Electron or Tauri window. The shell owns the window, menus, tray, file dialogs and auto-update. A target plugin typically writes the shell manifest in onAfterBuild, exposes native helpers through client.context, and sets baseURL when assets load from the filesystem instead of a server.

Installers, signing and notarization stay with the shell toolchain. Coralite produces the bundle those tools package.

5. Mobile shell

Package the same output in a Capacitor or WebView shell. The adapter supplies storage, notifications, permissions, share sheet, back navigation and deep links. Absolute route links must be reconciled with the shell origin, and the back gesture must be mapped to the router or to history; both belong in the adapter, not in every component.

6. Request-time rendering

The default build is static, but the library can render on demand with createCoralite() and build(path, options). That is how the CSP nonce example works: one request, one nonce, one rendered document. Framework server() blocks still do not receive a request or response object, so session data comes from a plugin or from the caller.

import { createCoralite } from 'coralite' const coralite = await createCoralite({ pages: './src/pages', components: './src/components' }) const [page] = await coralite.build('/dashboard/', { nonce })

7. Choosing a delivery

Need Delivery Trade-off
Search, sharing, zero installStatic web outputFull page navigation unless the router is added
Signed-in user dataStatic shell plus client fetchOne extra request after hydration
Persistent client state across routesSPA router pluginOutlet swap and guard management
Icon and offline startInstalled webManifest, service worker and cache strategy
Local files, menus, trayDesktop shellPackaging, signing and update channel
Store distribution and native APIsMobile shellPermissions, bridge and back-navigation mapping

The component tree and state model do not change between rows. Only the adapter and the platform-facing components change.

8. Build performance

Production builds are incremental: unchanged pages are reused, and the manifest records what each output depends on. A few configuration options control how much work a build does and how that work is measured.

Concurrency and workers

build.concurrency caps how many pages are processed at once; when it is not set, Coralite uses min(availableParallelism(), 8). A build() call can override it per build with maxConcurrent, and onBeforeBuild can change that option before rendering starts. Concurrency interleaves asynchronous work; SSR itself still runs on one event loop.

There is deliberately no build.workers flag. Page rendering depends on non-cloneable framework context and parent-affine plugin hooks, so moving it into workers would require reimplementing the renderer in each worker. The full analysis and a bounded process-sharding proposal are in the build workers design spike.

Incremental invalidation

An output is rebuilt when any of its recorded inputs changes:

  • Source hash: the page or component HTML changed.
  • Content key: contentKey() replaced the default hash of route params and resolved state. A page can also declare shouldSkipRender() to avoid calling server() for unchanged outputs; see the page API reference for the contract.
  • Runtime chunk: the shared client runtime changed.
  • Locale chunk: when i18n is enabled, only pages of the locale whose config chunk changed are rebuilt.
  • Component hashes and assets: a component, stylesheet, page script or injected asset changed. This is also the self-healing path when an output file is missing from disk.

Skipped pages carry their metadata forward, so a warm build does not lose chunk references or tracked assets.

Manifest storage

The incremental manifest is written compactly by default. build.manifestShards is an experimental option that stores it as hash-bucketed shard files; at 45,000 entries the sharded form measured slower to load than the compact single file and saved no bytes, so the default is recommended unless smaller individual files are required.

Benchmarking a build

Coralite ships internal suites for cold, warm and one-record-change builds, manifest storage, and locale chunk isolation:

pnpm bench:internal --suite=build-performance --rows=2000 --iterations=5 --task-id=my-build --phase=before --save pnpm bench:internal --suite=manifest-store --store=all --iterations=5 --task-id=my-manifest --phase=after --save pnpm bench:internal --suite=locale-chunks --mode=all --iterations=5 --task-id=my-locales --phase=after --save

Use distinct task IDs for before and after runs: --phase is metadata only and does not change the filename. Each saved result records the commit, a fingerprint of the benchmark suite sources, and whether the working tree was dirty, so pairs from different runs can be compared. Results are committed under benchmarks/results/; see the benchmark README for the full suite list.
