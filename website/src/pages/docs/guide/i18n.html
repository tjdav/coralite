Internationalization (i18n)

Guide

Learn how to handle internationalization in Coralite including locale routing, message bundles, native Intl formatting, RTL layout support, and framework boundaries.

Coralite leverages standard Web Platform APIs and explicit dynamic page routing patterns for internationalization. Rather than adding custom framework abstraction layers or proprietary translation utilities, Coralite provides simple building blocks that work seamlessly with native JavaScript features like Intl and JSON imports.

1. Locale Routing

Organize your localized pages using directory parameters such as pages/[lang]/ instead of language-prefixed filenames. This ensures every locale shares the same page template and logic structure while generating discrete localized routes at build time.

pages/ [lang]/ index.html about.html

Use flat named exports with the paths function to enumerate supported locales and inject the active locale parameter into the page state via the server block:

const locales = ['en', 'fr', 'de', 'ar'] export function paths () { return locales.map(lang => ({ lang })) } export function server ({ route }) { return { lang: route.params.lang, supported: locales.includes(route.params.lang) } }

Using pages/[lang]/ guarantees that locale paths are statically rendered as separate pages (for example /en/, /fr/, /de/, and /ar/) without duplicating template files.

2. Message Bundles

Translation bundles can be stored in standard JSON files and imported directly using ESM JSON import attributes. In the page's server() block, select the dictionary matching the active locale route parameter.

import messages from '../../../content/messages.json' with { type: 'json' } export function server ({ route }) { return { dictionary: messages[route.params.lang] ?? messages.en } }

In your HTML template, bind translation strings using flat template tokens. A dictionary object is not a token, so expose the string you need as a getter or a server return value.

export const getters = { welcome: ({ state }) => state.dictionary.welcome } <h1>{{ welcome }}</h1>
Flat Template Tokens Requirement

Coralite template tokens are flat identifiers, not paths. {{ t.welcome }} and {{ t.home.title }} are both rejected as CORALITE-E201. Flatten the value you need into a getter or a server return key, then bind the flat token.

3. Formatting

For formatting dates, numbers, currencies, or lists, rely directly on browser and Node.js native Intl.* APIs inside getters or server(). Do not wrap Intl in framework-specific helper utilities—native platform APIs are already built-in and performant.

export const getters = { formattedDate: ({ state }) => new Intl.DateTimeFormat(state.lang, { dateStyle: 'long' }).format(state.publishedAt), formattedPrice: ({ state }) => new Intl.NumberFormat(state.lang, { style: 'currency', currency: 'EUR' }).format(state.price) }

4. Right-to-Left (RTL) Support

Support right-to-left languages (like Arabic or Hebrew) by determining text direction in your server() function and binding the dir attribute on the <html> element:

export function server ({ route }) { return { dir: route.params.lang === 'ar' ? 'rtl' : 'ltr' } }

When writing component styles, use CSS logical properties instead of physical directions. For example, use margin-inline-start instead of margin-left, and padding-inline-end instead of padding-right. This ensures styles adapt automatically when switching between LTR and RTL directions without needing direction-specific CSS overrides.

Locale config chunks

When a dictionary is authored in plugin client config rather than in page state, a copy edit normally changes the shared client runtime and rebuilds every page. With i18n configured, Coralite splits the locales field of each plugin's client.config into small hashed chunks. Only pages whose route locale matches the edited chunk are rebuilt; the shared runtime chunk stays unchanged.

export default defineConfig({ i18n: { locales: ['en', 'fr'], defaultLocale: 'en' } }) export default definePlugin({ name: 'i18n', client: { config: { locales: { en: { welcome: 'Welcome' }, fr: { welcome: 'Bienvenue' } } }, init: ({ config }) => { window.__coralite__.plugins.i18n = { dictionary: config } } } })

The locale is taken from route.params.lang (or route.params.locale); pages without either use defaultLocale. Locale overrides are merged into the config passed to plugin init() in the browser. This does not partition dictionaries written directly inside a plugin's context closure: those are baked into the shared runtime chunk and still rebuild every locale. Keep dictionaries in page state when getters or templates need them.

State dictionaries are already per-page. Return only the active locale's slice from server() — messages[route.params.lang] — so the content key changes only for that locale. Returning the whole multi-locale object would put every translation into every page's key, so a single copy edit would rebuild all locales. If the full object must be kept in state, declare a contentKey() that hashes only the active locale's slice.

5. What Coralite Does Not Provide

To remain lightweight, predictable, and standards-compliant, Coralite intentionally does not ship built-in abstractions for several i18n concerns:

  • No plural rule engine: Use native Intl.PluralRules directly in your getters or server functions.
  • No Accept-Language detection: Language detection and initial redirection should be performed by host servers (e.g., Cloudflare Workers, Nginx, Vercel Edge) or lightweight client-side scripts.
  • No message extraction tooling: Use standard build-time script utilities or external tools if you need to scan source files for missing translation keys.
  • No translation management: Use external localization services (TMS) or translation platforms to manage dictionary translation workflows.
