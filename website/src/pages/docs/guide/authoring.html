Authoring Pattern

Coralite enforces a single, predictable authoring pattern across every layer of the application. Whether you are defining a Web Component, an HTML page, or a custom plugin, code is organized into named blocks inside a default export function imported from coralite.

Every entry point in Coralite—defineComponent, definePage, and definePlugin—accepts a configuration object composed of standard blocks. They share the same import source, default export convention, and static validation model.

import { defineComponent, definePage, definePlugin } from 'coralite' export default defineComponent({ /* component blocks */ }) export default definePage({ /* page blocks */ }) export default definePlugin({ /* plugin blocks */ })

Each block serves a clear, specific role during build-time rendering, runtime reactivity, or lifecycle execution.

Coralite templates use flat {{ token }} interpolations exclusively. To keep templates fast, deterministic, and statically indexable, templates forbid expressions, function calls, inline event handlers (such as onclick="..."), conditionals, and loops. All derivation logic must live inside getters.

{{ fullName }}

{{ user.firstName + ' ' + user.lastName }}

Top-level imports are reserved for defineComponent, definePage, definePlugin, and ESM modules used by isomorphic blocks (such as getters, style, or slots). Node-only dependencies used strictly in server() or paths(), and browser-only dependencies used in client(), must be imported dynamically using await import(...) inside the respective block.

import { definePage } from 'coralite' export default definePage({ async server () { // Correct: Node module loaded inside server() const fs = await import('node:fs/promises') const data = await fs.readFile('data.json', 'utf8') return { content: JSON.parse(data) } }, async client () { // Correct: Browser module loaded inside client() const { animate } = await import('https://esm.sh/motion') animate('.card', { opacity: 1 }) } }) // Bad: Importing Node/Browser modules at top-level pollutes bundle scope import fs from 'node:fs/promises' import { animate } from 'motion' import { definePage } from 'coralite'

Coralite draws a strict boundary between build-time server execution and browser client runtime execution. The server() function runs in Node.js during build/SSG and its return value is serialized to JSON. The client() function runs in the browser and cannot close over outer module scope variables populated during server() execution.

import { defineComponent } from 'coralite' export default defineComponent({ // 1. Runs at build-time in Node.js server () { return { serverTime: new Date().toISOString() } }, // 2. Runs in the browser runtime; receives serialized state client ({ state }) { console.log('Server rendered at:', state.serverTime) } })

Coralite guarantees that all context parameters destructured in block function signatures exist. Authors must not write defensive guards (such as if (!lists) return or if (state == null) return) against destructured context keys or guaranteed framework properties.

import { defineComponent } from 'coralite' export default defineComponent({ // Correct: Destructure directly without defensive checks client ({ state, refs, signal }) { const btn = refs('button') btn.addEventListener('click', () => { state.count++ }, { signal }) } })
