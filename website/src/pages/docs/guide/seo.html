Search Engine Optimization (SEO)

Guide

Web-target metadata patterns: head extraction, canonical URLs, Open Graph, sitemaps, feeds and JSON-LD.

This is a web-target concern.

Search crawlers, canonical URLs and social previews only apply when the output is served as a website. A desktop or mobile shell still ships the same HTML, but it does not need a sitemap or a canonical URL. Keep these concerns in head components and plugins, not in core.

1. Built-in metadata extraction

Coralite ships a built-in metadataPlugin that runs during page collection. It scans the <head> of the page and populates page.meta.

  • Title: the text of <title> is stored as page.meta.title.
  • Meta tags: <meta name="X" content="Y"> is stored as page.meta.X.
  • Language: the lang attribute on <html> is stored as page.meta.lang.

Only name="..." attributes are extracted. property="og:..." and name="twitter:..." tags pass through to the output untouched; section 3 shows how to build them.

Keys are stored verbatim, so <meta name="publishDate"> becomes page.meta.publishDate and a hyphenated key stays hyphenated. Templates only accept flat tokens, so map arbitrary keys to state in server() or a getter before rendering them.

Components on the page read the result in server() or getters:

<template id="page-header"> <h1>{{ title }}</h1> <p>{{ author }}</p> </template> <script type="module"> export function server ({ page }) { return { title: page.meta.title, author: page.meta.author || 'Coralite Team' } } </script>

The plugin also evaluates custom components inside <head>, so a reusable seo-bundle component can generate the tags that are extracted.

2. Canonical URLs

Canonical URLs depend on the deployment origin and on which routes are duplicates. That is a web-target decision, so core does not derive them. Build the URL where the route and origin are known, then render one canonical link.

export const meta = { siteUrl: { type: String, default: 'https://example.com' } } export function server ({ state, route }) { return { canonicalUrl: `${state.siteUrl}${route.path}` } }

In practice, the origin can come from a plugin or an environment-backed build option, while the path comes from route.path. Render it in the page head:

<link rel="canonical" href="{{ canonicalUrl }}">

For a site-wide rule, put the derivation in one head component rather than repeating it on every page.

3. Open Graph and Twitter Cards

These tags are ordinary HTML. The metadata plugin does not extract them, but it does not need to: write them in the head, or build them in a head component from page state.

<head> <meta property="og:title" content="{{ ogTitle }}"> <meta property="og:description" content="{{ ogDescription }}"> <meta property="og:type" content="website"> <meta name="twitter:card" content="summary_large_image"> <meta name="twitter:title" content="{{ ogTitle }}"> </head>

A component can compute the values from page.meta, the route or a post record, which keeps the tags consistent across a section without duplicating markup.

4. Sitemap generation

A sitemap is a build artifact, so a plugin writes it. onAfterBuild receives the rendered results; filter pages and use result.route.path. app.writeFile writes into the configured output directory.

import { definePlugin } from 'coralite' const siteUrl = 'https://example.com' function escapeXml (value) { return String(value) .replaceAll('&', '&amp;') .replaceAll('<', '&lt;') .replaceAll('>', '&gt;') } export default definePlugin({ name: 'sitemap', server: { async onAfterBuild ({ results, app }) { const pages = results.filter((result) => result.type === 'page' && result.status !== 'failed') const urls = pages.map((result) => ` <url>\n <loc>${escapeXml(siteUrl + result.route.path)}</loc>\n </url>`) const xml = [ '<?xml version="1.0" encoding="UTF-8"?>', '<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">', ...urls, '</urlset>' ].join('\n') await app.writeFile('sitemap.xml', xml) } } })

Exclude private routes by filtering result.route.path or by checking page metadata. The plugin has the full result list, so the rule stays in one place.

5. RSS and Atom feeds

Feeds are also build artifacts. Read the source data inside the hook, or collect it during an earlier hook, then write the XML with app.writeFile.

import { definePlugin } from 'coralite' const siteUrl = 'https://example.com' function escapeXml (value) { return String(value).replaceAll('&', '&amp;').replaceAll('<', '&lt;').replaceAll('>', '&gt;') } export default definePlugin({ name: 'feed', server: { async onAfterBuild ({ app }) { const fs = await import('node:fs/promises') const posts = JSON.parse(await fs.readFile('src/data/posts.json', 'utf8')) const items = posts.map((post) => [ ' <item>', ` <title>${escapeXml(post.title)}</title>`, ` <link>${siteUrl}/blog/${post.slug}/</link>`, ' </item>' ].join('\n')) const xml = [ '<?xml version="1.0" encoding="UTF-8"?>', '<rss version="2.0">', ' <channel>', ` <title>${siteUrl}</title>`, ` <link>${siteUrl}</link>`, ...items, ' </channel>', '</rss>' ].join('\n') await app.writeFile('feed.xml', xml) } } })

Escaping is not optional. A title containing & or < breaks the feed, so run user-authored text through an XML escape helper. Keep the feed format in the plugin so the page templates stay free of feed concerns.

6. robots.txt

Place robots.txt in public/. Coralite copies public assets to the output root verbatim.

User-agent: * Allow: / Sitemap: https://example.com/sitemap.xml

7. JSON-LD structured data

Script text is never token-interpolated. A JSON-LD block written in a template is shipped exactly as authored, which is usually what you want because JSON-LD must stay valid JSON.

<script type="application/ld+json"> { "@context": "https://schema.org", "@type": "Article", "headline": "A stable headline" } </script>

When the document must be generated from page data, a plugin can rewrite result.content in onAfterPageRender. That keeps the JSON producer in one place and avoids adding a raw-interpolation mode to templates. Render the JSON through JSON.stringify so escaping is correct.

8. What Coralite does not provide

These are intentionally not core features, because they only make sense for a web target and every site decides them differently:

  • Canonical derivation: compute it from route.path and your deployment origin.
  • Open Graph extraction: author the tags, or build them in a head component.
  • Sitemap and feed generators: write a plugin against onAfterBuild and app.writeFile.
  • Schema.org type definitions: write JSON-LD or use a schema helper library.

This is the same boundary described in Authoring Plugins: core owns the portable build, plugins own target-specific output.
