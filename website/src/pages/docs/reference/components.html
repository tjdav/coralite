Components Reference

Reference

The component module contract: eleven named exports, the order they run in, and where each one is specified in full.

This page is the map. Each export has its own reference page with a signature, its context, its behaviour and the diagnostics that guard it. Start here to see how the pieces fit, then follow the link for the block you are writing.

Component structure

A component is one HTML file. The template is markup; the module script exports behaviour; the style element holds the component's CSS. All three are siblings:

<template id="user-profile"> <div class="card"> <h2>{{ name }}</h2> <p>{{ role }}</p> </div> </template> <script type="module"> export const attributes = { userId: { type: String, required: true } } export async function server () { return { name: 'Alex Developer', role: 'Core Contributor' } } </script> <style> .card { padding: 1rem; border-radius: 8px; } </style>

The parser also accepts <style> and <script type="module"> nested inside the template and normalizes them to this form. Prefer the sibling layout in hand-written components.

The template id is the custom element name. It must be a valid custom element name, so it needs a hyphen. A component with no script at all is still valid: it renders, it is bundled, and it runs no client lifecycle code.

Exports

Handlers are declared with export function; configuration with export const. The compiler reads both the export form and the name, and ignores helper exports it does not recognise.

Export Form Runs Purpose
attributes export const Build + browser Declares, coerces and validates host attributes.
server export function Build Loads data in Node and merges the result into state.
getters export const Build + browser Derives values from state.
style export const Build + browser Maps state onto host inline styles and custom properties.
slots export const Build + browser Transforms projected children before distribution.
provide export const Build + browser Broadcasts values to descendants through the context protocol.
consume export const Build + browser Subscribes to an ancestor's provided value.
formControl export const Browser Opts into Form-Associated Custom Element behaviour. The legacy alias is formAssociated.
listStrategy export const Browser Chooses a full reactive update or a direct DOM patch for observed list changes.
onError export function Production build Renders fallback markup when the component fails during SSR.
client export function Browser Binds events, observes state and owns the instance lifecycle.

defineComponent still works for existing components. New components use named exports; the wrapper adds nothing at runtime and is easier to tree-shake when it is absent.

Execution order

  1. Attributes are read from the host markup, coerced and validated. The result is the initial state.
  2. server() runs in Node and its return value is merged into state.
  3. getters evaluate in declaration order, then again in the browser when their dependencies change.
  4. slots run as the template is rendered, transforming the children the page projected.
  5. The template renders with flat tokens resolved from state.
  6. client() runs once in the browser after hydration, then owns listeners and observers until disconnect.

Only the first four can change what the server sends. client() cannot influence the initial HTML, which is why data needed at first paint belongs in server().

Shared rules

  • Flat exports only. No nested configuration object, no default export for new code.
  • Templates use flat tokens. No expressions, dot paths or function calls. Lift them into getters.
  • Primitives in attributes. Structured data goes through server() or context, never through an attribute.
  • No defensive guards. The context object is guaranteed. Branch with isServer, never with typeof window.
  • No module-scope imports in client(). Load what the browser needs with await import() inside the block.
  • Getters are isomorphic. Server-only plugin data must be written to state in server() before a getter reads it.

Async getters are the one asymmetry: the server skips them, so the token renders empty at first paint and resolves in the browser. Use them for interaction-driven data, not for content that must be indexed or visible before JavaScript runs.

Static means no lifecycle.

A component with only a template and a style, or a script that exports nothing but attributes, ships no client lifecycle code. That is the zero-JS case: markup and CSS, no hydration work.

Error boundaries

In production, a component that throws during SSR can render fallback markup through onError. In development the error is thrown with the component id and file, which is deliberate: the boundary is an availability tool, not a debugging aid.

Unhandled failures mark the affected page as failed while sibling pages complete. A page-level onError can replace the entire document instead.

Authoring checklist

  • The template id matches the file name and contains a hyphen.
  • Every ref is read in client(), or the warning is suppressed with a pragma.
  • Every attribute has a type, and required is not paired with default.
  • Getters compute rather than alias state.
  • Style functions return strings or null, with units where CSS needs them.
  • Data needed before JavaScript runs is loaded in server().
